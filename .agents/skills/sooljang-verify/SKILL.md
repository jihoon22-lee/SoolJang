# 변경 검증과 증거

저장소 루트의 `docs/development.md`에서 명령·환경·필수 검사 범위를 확인한다. 현재 diff와
담당 WP의 R/S 수용 기준으로 필요한 검증을 고른다. 다른 스킬을 읽는 것은 필수 단계가 아니다.

- 구현 중에는 관련 테스트부터 돌린다. 제출 전 Ruff·ty·웹 check와 해당 변경에 필요한
  회귀 검증을 완료한다. 기존 커버리지/required CI를 낮추거나 실패 테스트를 제거하지 않는다.
- 문서/지침 변경은 링크·명령·지침 충돌을 확인한다. 새 스킬은 사용 가능한 공식
  `skill-creator`의 `quick_validate.py`로 형식을 검사하고 현실적인 호출/비호출 예시도 검토한다.
  형식 통과를 실제 에이전트 행동 검증으로 보고하지 않는다.
- 백엔드/DB 변경은 격리 PostgreSQL에서, UI/PWA 변경은 해당 브라우저 시나리오까지 검증한다.
  외부 요청은 기본 CI에서 mock/fixture로 검사하고 opt-in 실연결의 범위·비용 권한을 별도 확인한다.
- DB fixture와 migration은 데이터를 지울 수 있다. 대상이 폐기 가능한 테스트 DB인지 확인하고
  같은 DB를 사용하는 pytest/migration/다른 에이전트 검증을 동시에 실행하지 않는다.
- 실패는 변경 때문인지 환경/기준선 문제인지 재현 근거로 구분한다. 동일 코드·환경·입력의
  성공 검증은 새로운 변경·실패·미해결 우려가 있을 때만 반복한다.

기록에는 관련 R/S, source SHA(미커밋이면 그 사실), fixture/schema·환경, 실제 명령 또는
run URL, 결과와 제한을 담는다. 결과는 통과·실패·미실행·조건부를 구분하고 DB skip,
mock 응답, HTTP 200을 실제 복구나 출처 수용의 대체 증거로 쓰지 않는다.
같은 PR의 workthrough를 갱신하며 전체 로그를 복사하지 않는다.
