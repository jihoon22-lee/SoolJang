- 요구사항: 리뷰 ②·④, QS03·QS17·QS19, D255. 2026-10-23 사용자 승인 범위.
- 코드 기준: `35efbd4`, 확정 409 후속 `35b8016`·주석 정정 `ee29441`, 라벨 경계 `71142b4`. F1 #182·F3 #183·F5 #184와 공통 보안 패치를 통합한다.
- 데이터/권한: schema 0021·API·인증·소유권 유지. 탭·계정별 기존 sessionStorage 요청 키에

## 변경

온라인에서 제품·구매를 한 번 전송한 등록은 오프라인 새 생성으로 전환하지 않는다. 성공한
제품과 구매 단계를 건너뛰고 미확정 단계는 같은 payload와 request key로 확인한다. 409나
재확인의 422가 원래 요청을 자동으로 잊게 하지 않는다. 제품 생성의 확정 409는 목록 확인과
명시적 중단을 제공하며, 첫 요청의 확정 422는 입력 수정을 허용한다.
미확정 구매의 구매처 ID·SKU도 고정하며, 재조회한 제품에서 첫 SKU를 임의로 고르지 않고 원래
용량과 하나만 일치할 때 구매를 생성한다. 규격이 사라졌으면 부분 실패와 입력을 유지한다.

저장 중 입력·닫기·복원·재제출을 막고 같은 탭에서 화면을 다시 열어도 진행 상태를 이어 본다.
성공은 제출한 초안 버전·계정 세대·폼 인스턴스를 확인해 정리한다. 이후 입력은 지우지 않으며,
이미 만들어진 술에 연결된 입력으로 안내한다. 새 등록으로 복제하려면 남은 입력 폐기를 명시적으로
확인한다. 새로고침 후 필요한 사진만 다시 선택할 수 있다. 매장 모드와 제품 수정에도 같은 초안
보존 원칙을 적용했다. 탭 자체를 닫은 뒤 요청 키를 복구하는 기존 이연 범위는 확대하지 않는다.

## PR #185 자동 리뷰 후속

[확정된 제품 생성 충돌](https://github.com/jihoon22-lee/SoolJang/pull/185#discussion_r4358865414)은
제품 ID가 없어 입력 폐기도 할 수 없던 결함이었다. 요청 지문 불일치·만료·생성 제품 삭제처럼 같은
요청으로 복구할 수 없는 409를 별도 상태로 보관하고, 자동 재전송을 막았다. 목록 확인·닫기·재열기와
중단 취소는 요청/입력을 유지한다. 사용자가 경고를 읽고 명시적으로 중단해야 키와 입력을 정리한다.
계정 세대·초안 버전이 바뀌면 그 중단도 적용하지 않는다. 중단 자체는 서버 쓰기를 실행하지 않는다.

- 수정 전 hook/UI 회귀 5개 실패·33개 통과 → 관련 4파일 81개 통과(9.33초).
- 변경 7파일 Biome, typecheck, production build, `git diff --check` 통과.
- 실제 격리 API에서 합성 제품의 생성 응답을 잃게 한 뒤 그 제품을 삭제했다. 같은 요청의 실제 409,
  새로고침·목록 확인·중단 취소의 보존, 확인 뒤 요청 정리, 다음 사용자 제출의 새 키/201을 확인했다.
  명시 중단 시 생성 요청 0건, 앱의 삭제 요청 0건, 새로 등록한 제품 1건, page error 0건이었다.
- [실제 API 결과](assets/2026-10-23-review-product-save-recovery/terminal409-results.json)와
  [중단 확인 화면](assets/2026-10-23-review-product-save-recovery/07-product-conflict-explicit-confirmation.png).
- 독립 루트 검토에서 미확정 실패를 임의 중단할 수 없고 확정 409만 명시 중단한다는 경계를 확인했다.
  마지막 전체 검사와 보안 감사는 이 보완을 포함한 PR CI·통합 버전 PR에서 확인한다.

## 전송 전·최초 확정 거절의 라벨 복구 후속

[PR #186의 라벨 지적](https://github.com/jihoon22-lee/SoolJang/pull/186#discussion_r4359022500)을
F2의 공통 hook에서 보완했다. 오프라인에서 사진이 있는 등록을 처음 거절할 때 전송 전 사진을 복구
상태로 남겨, 폼을 닫고 다른 제품을 작성해도 그 사진이 붙을 수 있었다. 독립 검토에서 최초 확정
422와 요청 키만 남은 오프라인 재시도가 같은 상태를 다시 만드는 경로까지 확인했다.

전송 전 거절과 최초 확정 422는 복구 메타데이터·임시 File만 정리한다. 실제 폼 초안·현재 폼이
명시적으로 전달하는 사진·요청 키는 유지한다. 응답을 잃은 뒤의 422, 이미 만든 제품·구매, 실제
전송 payload가 있는 요청은 계속 보존한다. 키만 존재하는 거절을 실제 전송 이력으로 저장하지 않는다.

- 잘못된 사진 첨부의 수정 전 실패와 요청 키만 있는 재시도 실패를 확인했다.
- 최종 관련 7파일 100개(핵심 90개·오프라인/세션 10개), lint·typecheck·build·diff check 통과.
  lint의 기존 경고 18개는 실패가 아니며 이번 보완에서 늘지 않았다.
- 루트가 최종 조건과 초기 거절·확정 거절·결과 미확정의 경계를 다시 검토했다.
- 새 UI를 추가하지 않았으며 사진 재선택 안내 문구만 맞췄다. 이 보완의 DB·실브라우저 재실행은
  하지 않았다. 위 실제 브라우저 10개 결과와 이번 hook 회귀의 검증 범위를 구분한다.
