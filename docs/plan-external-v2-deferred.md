# 외부 정보 조회 v2 — 보류 범위 (Task 34 / 2단계)

`docs/plan.md` §4 Task 34 중 **사용자 입력이 있어야 진행되는 PR** 만 모았다. 지금 바로
착수 가능한 범위는 [plan-external-v2.md](plan-external-v2.md) 에 있고, 그쪽이 현재 작업
대상이다.

이 문서는 **계획과 체크리스트만** 담는다. 설계 세부(변경 파일 목록, 개별 테스트 케이스,
API 계약)는 차단이 풀려 실제로 착수할 때 그 PR 의 계획으로 확정한다 — 특히 사이트 추가
(PR8~PR10)는 실제 응답 모양을 보기 전에 쓴 세부 설계가 추측이 되기 쉽다.

PR5~PR7 은 "약함"이라 사실상 **답 하나만 주면 바로 착수**할 수 있다. PR8~PR10 만 본격적인
협업이 필요하다.

### 근본 원인은 열린 질문이 아니라 환경 제약이다

PR8~PR10 이 막히는 진짜 이유는 질문이 아니라, **개발 샌드박스에서 외부 도메인 DNS 조회
자체가 안 된다**는 것이다(`plan.md` Task 18 절, 2026-08-03 확인 — `example.com` 조차
`ETIMEOUT`). GitHub·PyPI·npm 등 소수 호스트로만 아웃바운드가 열려 있다. 추측으로 셀렉터를
쓰면 배포된 프리셋이 조용히 깨진다.

#### 협업 루프 (사이트 1곳당)

| 단계 | 담당 | 산출물 |
|---|---|---|
| 1 | 사용자 | `https://<사이트>/robots.txt` 원문 |
| 2 | 사용자 | 브라우저 DevTools → Network 탭에서 검색 시 실제로 나가는 요청의 URL·메서드·필수 헤더, 그리고 응답 샘플 (JSON 이면 그대로, HTML 이면 상품 카드 부분) — **쿠키·세션·개인정보는 제거해서** 전달 |
| 3 | 개발 | 프리셋 작성 + 그 샘플을 fixture 로 넣은 오프라인 테스트 |
| 4 | 사용자 | 배포 환경(홈 PC)에서 실제 제품 3종으로 조회 확인 + 결과 스크린샷 |
| 5 | 개발 | 어긋난 부분 수정 → 머지 |

2단계 샘플은 `tests/fixtures/external/<사이트>.json` 으로 커밋한다 (절대 규칙 4 —
익명화·축약 fixture 만).

#### 사이트별 사전 판단 기준

각 사이트를 붙이기 전에 확인하고 **결과를 문서에 남긴다.** 하나라도 막히면 등록하지 않고
사유를 기록한다 — 어댑터가 robots 차단 시 `degraded` 를 반환하긴 하지만, 애초에 못 쓸
프리셋을 배포하지 않는 게 맞다.

1. `robots.txt` 가 검색·상세 경로를 허용하는가
2. 이용약관이 자동화 접근을 금지하지 않는가
3. 공식 API 가 있는가 (있으면 스크래핑보다 우선)
4. 로그인 없이 검색 결과에 접근 가능한가

## 3. PR5 — 소스 프리셋 카탈로그와 `adapter_spec` v2 (방안 H)

> 브랜치 `feat/external-source-presets` · 마이그레이션 `0011_source_presets_credentials` · 결정 D186~D188

### 목적

소스 등록 비용을 "JSON 을 손으로 쓰기"에서 "목록에서 고르기"로 낮추고, 사이트 개편 시
**앱 업데이트로 스펙을 갱신**할 수 있게 한다. PR8~PR10 의 선행 조건이다.

### 계획 요지

- `src/sooljang/infrastructure/external/presets/*.yaml` + 로더. 각 프리셋은 `key`·`name`·
  `base_url`·`description`·`category_hint`·`requires_credentials`·`version`·`adapter_spec`
- `external_source` 에 `preset_key`·`preset_version`·`spec_overridden` 컬럼 추가.
  사용자가 스펙을 직접 손대면 `spec_overridden=True` 가 되어 **앱 업데이트가 사용자 편집을
  덮어쓰지 않는다**
- `adapter_spec` v2 확장 — `search.method`(POST)·`search.body`·`search.headers`·
  `credentials`·`transform: strip_tags`. `version: 1` 스펙은 그대로 동작한다
- 자격 증명은 새 테이블 `external_source_credential` 에 Fernet 암호문으로 저장
  (`LlmSetting` 패턴 재사용). **요청 직전에만 복호화해 주입하고 로그·`raw_excerpt`·에러
  메시지에 절대 남기지 않는다**
- 번들 프리셋 전부를 스키마 검증하는 CI 가드 — 네트워크 없이 실행되며, 프리셋 오타가
  사용자에게 배포되는 것을 막는다
- 기존 커스텀 등록 경로(JSON textarea)는 그대로 둔다. 프리셋은 추가 선택지다

### 왜 데일리샷 스펙 원문이 필요한가

그 스펙은 **저장소 어디에도 없다.** `docs/plan.md` D147 에 엔드포인트
(`api.dailyshot.co/items/search/`)와 대략의 모양만 적혀 있고, 실제 등록된 JSON 은 사용자
DB 안에만 있다. 추측으로 복원하면 §1 에서 경고한 그대로 조용히 깨진다.

### 체크리스트

- [ ] 데일리샷 `adapter_spec` 원문 확보 (사용자)
- [ ] 프리셋 로더 + 카탈로그 API + `SourcesPage` "추천 소스에서 추가" UI
- [ ] `adapter_spec` v2 확장 (method·headers·body·credentials·`strip_tags`)
- [ ] 자격 증명 Fernet 저장 + **유출 방지 테스트**(로그·응답 전체 문자열 검사)
- [ ] 프리셋 버전 갱신이 `spec_overridden=False` 소스만 건드리는지 테스트
- [ ] v1 스펙 하위 호환 테스트
- [ ] 번들 프리셋 스키마 검증 CI 가드

## 4. PR6 — 애매 구간 LLM 재판정 (방안 E)

> 브랜치 `feat/external-llm-rematch` · 마이그레이션 없음 · 결정 D189~D190

### 목적

즉시 착수 범위 PR1 의 "확인 필요" 구간(0.5~0.85)에서 사용자를 귀찮게 하는 빈도를 줄인다.

### 왜 ToS 위험이 없는가

D167 에서 폐기한 `search` 전략은 **검색엔진 결과를 스크래핑**하는 것이었다. 이것은 다르다
— **이미 정당하게 받아온 후보 목록 안에서 고르는 것**뿐이고, 외부 사이트에 추가 요청이
나가지 않는다. LLM 에는 상품명 문자열만 전달한다.

### 계획 요지

- 신규 `infrastructure/external/match_llm.py`. `llm.py::LabelExtraction` 의 구조화 출력
  패턴을 그대로 쓴다
- 호출 조건 **전부** 만족할 때만: ① 최고 점수가 0.5~0.85 구간 ② `LlmSetting` 활성
  ③ 사용자가 설정에서 "LLM 매칭 보조"를 켬 (기본 **꺼짐**)
- 입력은 내 제품 메타데이터 + 후보 최대 5개의 **이름만**. 가격·URL·후기는 보내지 않는다
- **자동 고정하지 않는다.** "LLM 추천" 배지를 붙여 사용자 확인을 받는다 — 자동 고정은
  오답을 영구화하고, PR1 의 "고정은 사용자 명시 조작으로만" 원칙과 어긋난다
- 실패·타임아웃·미설정 → 조용히 기존 경로로 폴백. 예외를 밖으로 내보내지 않는다
- 비용 가드: 조회 1건당 최대 1회, 같은 (제품, 소스) 조합은 24시간에 1회, **월 상한**(Q10)

### 체크리스트

- [ ] Q10 답변 확보 — 또는 보수적 기본값을 제안해 착수
- [ ] 기본값이 꺼짐이고, 켜지 않으면 OpenAI 호출이 0건임을 테스트로 확인
- [ ] 자동 채택 구간·미설정·설정 꺼짐에서 호출하지 않음을 테스트
- [ ] 타임아웃 시 기존 점수 결과로 폴백, 예외 없음
- [ ] LLM 추천이 자동 고정되지 **않음**을 테스트
- [ ] 비용 상한 정책을 결정 로그에 기록

## 5. PR7 — 제외 키워드 (방안 F)

> 브랜치 `feat/external-exclude-keywords` · 마이그레이션 없음 · 결정 D191

### 계획 요지

`adapter_spec.search.exclude_keywords` — 후보 이름에 이 단어가 있으면 후보에서 뺀다.
소스 컬럼이 아니라 **스펙 안에 두는 이유**: 프리셋으로 함께 배포·갱신되어야 하기 때문이다.

주의: 단순 부분 문자열 매칭은 오작동한다(`잔` 이 `잔티`·`발란자`에 걸린다). 즉시 착수
범위 PR2 의 토큰 집합을 재사용해 **토큰 단위로** 비교한다.

### 목록을 언제 확정하는가

**메커니즘은 지금도 만들 수 있지만 목록은 실측이 있어야 채워진다.**

| 단계 | 근거 | 내용 |
|---|---|---|
| 초안 | 데일리샷 실사용 | `잔`, `글라스`, `디캔터`, `미니어처`, `공병`, `굿즈`, `안주`, `선물세트`, `쇼핑백`, `보관함` |
| 확정 | PR8~PR10 실측 | 각 사이트에서 실제로 걸린 비주류 상품을 보고 소스별로 보강 |

초안은 데일리샷 하나만으로도 근거가 서는 항목만 담는다 — 붙이지도 않은 사이트를 상상해
채우지 않는다. 네이버 쇼핑(PR8)은 주류 통신판매 제한 때문에 제외어가 특히 많이 필요할
것으로 보이지만, 그건 실측 후에 넣는다.

### 체크리스트

- [ ] 제외어 없는 기존 스펙은 동작이 변하지 않음

- [ ] PR8~PR10 중 실제로 머지된 사이트의 실측 제외어가 반영됨

## 6. PR8 — 공식 API 소스: 네이버 쇼핑·Untappd (방안 I)

> 브랜치 `feat/external-api-sources` · 마이그레이션 없음 · 결정 D192~D193

공식 API 를 먼저 붙인다. ToS 가 명확하고, 셀렉터가 깨질 일이 없으며, PR5 의 `credentials`
경로를 실사용으로 검증한다.

### 네이버 쇼핑 검색 API

- `https://openapi.naver.com/v1/search/shop.json?query={query}&display=20`,
  헤더 2개(`X-Naver-Client-Id`·`X-Naver-Client-Secret`) → PR5 `credentials` 사용
- 응답 매핑: `items[].title`(→ `strip_tags` 필요), `lprice`→`price_krw`, `link`→url,
  `mallName`→`extra.mall`. `format: json` + `result_fields` 로 상세 조회 없이 완결
- **주의 1**: 주류는 온라인 통신판매가 제한돼 검색 결과가 잔·안주·굿즈·빈병 위주로 나올
  수 있다. 전통주·와인 일부는 정상적으로 잡힌다. 실측 후 **유지/폐기를 이 PR 안에서
  판단**하고, 유지하면 PR7 제외어 목록 초안을 여기서 수집한다
- **주의 2 (어댑터 수정 필요)**: 검색은 `openapi.naver.com`, 상세 링크는
  `smartstore.naver.com` 등 **다른 호스트**라 현행 `_same_host` 검증이 결과를 통째로
  버린다. 프리셋에 `link_hosts` 허용 목록을 두고, 상세를 조회하지 않는 `result_fields`
  모드에서는 링크를 표시 전용으로만 쓰게 한다 (조회하지 않는 URL 에 SSRF 위험은 없다)

### Untappd (맥주)

- 레거시 엑셀에 `U` 태그 평점이 19건 있다 — 사용자가 실제로 참고해 온 소스다
- API 키 발급에 승인 절차가 있다. **승인이 지연되면 이 PR 에서 빼고 뒤로 넘긴다**(Q11)
- `category_id` 를 맥주로 지정해 다른 주종 조회에서 빠지게 한다

### 체크리스트

- [ ] Q11 해결 — API 키 발급 주체 확정 및 발급
- [ ] 응답 샘플 확보 → fixture 커밋

## 7. PR9 — 평점 소스: Whiskybase·RateBeer·BeerAdvocate (방안 I)

> 브랜치 `feat/external-rating-sources` · 마이그레이션 없음 · 결정 D194~D195
