| D37 | 커서 페이지네이션 (`(정렬키, id)` 복합, 불투명 인코딩) | offset 은 데이터가 바뀌면 중복·누락이 생긴다. 정렬키만으로는 동일값 행에서 순서가 불안정하다. 불투명하게 만들어 클라이언트가 내부 구조에 의존하지 않게 한다 |

| D42 | 반응형은 CSS 만으로. 테이블·카드를 둘 다 렌더 | JS 뷰포트 감지는 초기 페인트에서 잘못된 뷰를 보이게 하고 테스트에서 한쪽만 검증된다 |
| D43 | 금액 표시 규칙을 `formatMoney` 한 곳에 고정 | `null` 은 0원이 아니라 가격 정보 없음이다. 컴포넌트마다 되풀이하면 언젠가 한 곳에서 빠진다 |

| D47 | 구매처 분할은 병수 힌트 합계가 맞을 때만 | 억지로 균등 분배하면 실제와 다른 금액이 기록된다. 실패 시 원문을 보존해 사용자가 나중에 쪼갠다 |

| D45 | 사진 첨부를 Task 13 으로 이동 | 첨부 API 가 아직 없고, 시음 사진이 필요한 Task 13 에서 업로드 저장소·검증·표시를 함께 다루는 것이 응집도가 높다 |

#### Task 12 결정 (D50~D56)

| # | 결정 | 이유 |
|---|---|---|
| D50 | 세션은 **서버 저장**, JWT 미사용 | 로그아웃·기기 분실 시 즉시 무효화가 필요하다. JWT 는 만료 전까지 유효해 회수할 수 없다 |
| D51 | 세션 토큰은 **해시만 저장** (SHA-256) | DB 가 유출되어도 세션을 재현할 수 없어야 한다. 비밀번호와 같은 등급의 비밀이다 |
| D52 | 비밀번호는 **Argon2id** | 현재 권장 기본값. 메모리 하드해서 GPU 공격에 강하다 |
| D53 | 인증을 **라우터 단위**로 적용 | 엔드포인트마다 붙이면 새 라우터에서 빠뜨려 조용히 공개된다. `app.py` 에서 한 번에 걸어 기본이 인증이 되게 한다 |
| D54 | CSRF 는 **double-submit cookie** | 세션을 서버에 저장하므로 토큰을 세션에 묶을 수도 있지만, `SameSite=Lax` 가 1차 방어이고 이 방식이 상태를 늘리지 않는다 |
| D55 | `Secure` 플래그는 **HTTPS 일 때만** | 로컬 개발은 평문 HTTP 라 항상 켜면 쿠키가 저장되지 않아 로그인이 안 된다. `X-Forwarded-Proto` 도 본다 |
| D56 | 테스트는 인증을 **우회하지 않는다** | 의존성을 오버라이드해 인증을 끄면, 인증이 깨져도 테스트가 초록색이라 알 수 없다. `api_client` 가 실제 `/auth/setup` 을 호출한다 |
| D57 | 비밀번호 변경 시 **다른 세션 전부 폐기** | 비밀번호를 바꾸는 이유는 대개 유출 우려다. 기존 세션을 살려 두면 바꾼 의미가 없다 |
| D58 | 레이트 리밋은 **인메모리** | 단일 사용자·단일 프로세스 전제. 여러 워커로 늘리면 공유 저장소가 필요해진다 |
| D59 | 백업은 `pg_dump -Fc` + **검증까지** | 파일이 존재하는 것과 복원 가능한 것은 다르다. `pg_restore --list` 로 실제로 읽어 본다 |

#### WP01 — 기록 보호·조건부 실행 취소

- **산출물:** 제출 시점의 대상·계정·입력 버전을 고정하는 공통 저장 계약. 빠른/상세 시음과
  구매 수정에 적용한다. 저장 중 입력·접기·취소의 정책을 일치시키며 이전 성공 콜백은

- **취소 계약:** 동작 직후의 병 revision/후속 명령을 검사한다. 같은 병에 시음·잔량·상태·
  소유 연결 변경이 있으면 거부하고 최신 상태를 보존한다. 다른 병의 변경은 허용한다.

- **호환성:** 기존 v1.8.2 PWA의 역전이 요청에도 서버가 후속 시음을 훼손하지 않는 안전 조건을
  적용한다. 새 취소는 원동작 ID·expected revision·멱등 키를 요구한다. 원동작/읽은 상태를
  알 수 없는 구버전의 `unopen/reopen/set_remaining` 요청은 안전성을 추측하지 않고

  실패로 남기며 성공/해결된 충돌로 소비하지 않는다. 새 클라이언트의 수동 잔량 정정도
  expected revision을 사용한다. 기존 조회·생성의 응답 형식은 유지하되 모든 구버전 역전이의

#### WP02 — 규격별 보유 현황·일관된 식별·이동

#### WP03 — 가격·재고 원가 공통 집계

- **산출물:** §4의 SKU별 계산과 제품 합계. domain·SQL·TypeScript에 같은 합성 정답을 적용한다.
  구매/병/규격 연결을 집계 입력에 보존하고, 같은 규격의 여러 구매·0원·부분 소진을 다룬다.
  API 응답은 SKU 요약을 추가하는 방식으로 확장하고 기존 제품 지표의 범위를 명시한다.
- **비교:** 매장 최근/최저/평균과 기존 외부 제안의 "내 가격 대비"에 선택 SKU를 사용한다.
  비교 가능한 내 구매가 없으면 비교 불가로 표시한다. 다른 규격은 ml 단위 환산과
  서로 다른 용량이라는 표시가 있을 때만 보조 비교하며 같은 규격 가격으로 표현하지 않는다.
  외부 취득·파싱·보관 정책은 변경하지 않는다.
- **성능:** SQL에서 제품별 반복 조회를 만들지 않고 SKU별 집계를 조인한다. IndexedDB
  카탈로그도 공통 조인 결과에서 파생해 목록 카드마다 DB를 다시 읽지 않는다.
- **수용:** S01~S03/S12의 계산, S13/S14의 계산 경로, S16의 변경 후 재계산, S18의

#### WP04 — 등록·재구매·가격 검색

구현·로컬 검증 완료. [실행 기록](../workthrough/2026-10-10-usage-purchase-flow.md)에 공유
필터 정답과 검증 범위를 모은다. 웹 872개·빌드 통과. UI 생성 흐름 10개와 모바일/재고 단독 조건 수정 후 2개 통과. Python 1,517개·커버리지 92.16% 통과. [#164 CI](https://github.com/jihoon22-lee/SoolJang/actions/runs/37968190547) 전체 통과·main `23d5c89` 통합.

- **산출물:** 규격이 이미 있어도 "다른 용량 추가"를 제공한다. 새 규격을 추가한 뒤 그 규격을
  선택한 구매 폼으로 돌아오며 날짜·구매처·가격·병수 입력을 보존한다. 같은 용량은 재사용하고
  동시 중복 추가는 409 후 기존 규격 선택으로 회복한다. 첫 규격 생성도 유지한다.
- **재구매:** 매장 모드의 기존 제품 이동을 실제 연결한다. 중복 후보는 이름만으로 확정하지
  않고 빈티지·도수 등 기존 제품 식별 기준을 함께 보여준다. 다른 빈티지를 강제 병합하지 않는다.
  스캔 결과의 SKU를 상세·매장 비교·구매 폼에 전달한다. 모르는 바코드는 확인 후에만 연결한다.
- **필터:** 구매처·구매일·용량 조건은 같은 구매 건에 AND로 적용한다. 재고 조건을 결합하면
  그 구매에 속한 현재 병을 검사한다. 제품/규격 요약의 전체 값과 필터에 맞는 값은 구분한다.
  목록 정렬은 제품 단위를 유지한다. 가격의 모집단·비교 기준·정렬 키는 §4.2로 고정한다.
- **규격 경계:** 구매가 연결된 SKU의 전역 용량 변경·삭제는 거부하고 구매 규격 정정으로
  안내한다. 사용하지 않은 규격만 수정·삭제할 수 있다. 온라인/sync에 같은 규칙을 적용하며,
  이미 부모가 삭제된 행은 원본을 보존하고 조회마다 살아 있는 연결 검사를 일치시킨다.

#### WP05 — 기록 찾기·안전한 정정

구현·로컬 검증 완료. [실행 기록](../workthrough/2026-10-10-usage-history-correction.md)에 정정·조회 경합과 초안/탐색 보호 검증을 모았다. Python 1,559개(92.11%)·웹 939개(branch 82.66%)와 합성 UI 정정·조회 흐름 9개를 단계별로 확인했다. [#165 CI](https://github.com/jihoon22-lee/SoolJang/actions/runs/37976242229) 전체 통과·main `a8d21ff` 통합.

- **찾기:** 제품/규격/병/기간으로 시음 목록과 요약을 읽고 커서로 끝까지 조회한다.
  각 기록에 판본·용량·병·구매 맥락을 제공하고 최근 시음 링크가 해당 기록에 도달하게 한다.
  기존 병별 배열/페이지 API는 보존한다. 처음/추가/갱신 실패를 구분하고 읽은 기록을 유지한다.
- **기록 정정:** 노트·평점·날짜 등 내용 수정은 기존 시음 ID를 유지한다. 날짜는 상태 전이
  제약과 함께 검증한다. 양·대상 병 정정은 기록 변경과 현재 병 상태/잔량을 별도 항목으로
  확인한다. 잔량을 바꾸기로 선택했을 때만 명시한 최종값을 같은 트랜잭션에서 반영한다.
  A병→B병 정정은 원래 병·대상 병 양쪽의 revision/현재 상태를 읽고 잠금 안에서 다시 확인한다.
  `tasting_session.bottle_id`와 `sku_id`를 함께 갱신하고 양쪽 병·SKU·제품의 요약을 무효화한다.
  원래 시음 ID와 첨부 ID는 유지한다. 화면에서 A/B 각각의 현재값→적용할 최종 상태·잔량을
  확인하며, 어느 쪽이든 동시 변경되면 전체 409로 무변경 처리한다. 같은 request_id 재요청은
  한 번만 반영한다. 과거 시음 전체를 재생해 현재 잔량을 자동 추정하지 않는다.
  기록 내용만 정정하기를 선택하면 양쪽 병의 잔량은 유지하며, 삭제만 해도 잔량은 그대로다.
- **구매 규격 정정:** 같은 제품의 목표 SKU로 구매 건을 이동하고 기존 구매·병·시음 ID를
  보존한다. 병에 연결된 `tasting_session.sku_id`도 원자적으로 정합성을 맞춘다. 다른 구매는
  바꾸지 않는다. 잔량이 새 용량보다 크면 묵시적으로 잘라내지 않고 명시적 최종값을 요구한다.
- **공통 안전 조건:** source/target 소유권·삭제 여부, 대상 revision, 잔량 범위, 날짜, 후속
  변경을 검증한다. 다중 병 잠금은 UUID 정렬 순서로 고정한다. request_id 멱등성과
  before/after 이력을 남긴다. 충돌은 409, 입력 보존 후 최신 상태를 다시 확인한다.
  정정은 온라인 전용으로 시작하고 오프라인에서는 초안·제한 이유를 보존한다.
- **수용:** S04, S08, S10~S11, S15~S20. 삭제→재등록을 정상 정정 경로로 사용하지 않는다.

2. §2.2에서 다음 WP와 선행 PR 상태를 확인한다. 담당 R, §4 계약, §6 시나리오만 추가로 읽는다.

4. 격리 DB 54329·별도 API/PWA 포트에서 구현과 실브라우저 검증을 수행한다. 운영 Compose를
   개발에 사용하지 않는다. 필요한 환경만 재개하며 동일 검증을 이유 없이 반복하지 않는다.
5. 필수 로컬 검사와 CI, 독립 회귀 검토를 마친 뒤 사용자 흐름의 결과를 기록한다.
   PR 상태·workthrough를 갱신하고 선행 수용이 완료된 다음 묶음으로 진행한다.

## 4. 공통 계약과 결정

아래는 v1.9.0에서 구현·수용한 실사용 흐름의 계약이다. 실제 결과는 WP06과 릴리스 실행 기록에 연결한다.

- **D231 — 표현 단위:** 사용자가 선택한 제품 한 항목＋규격별 재고·가격 구조를 사용한다.
  제품 정체성(이름·빈티지·도수), SKU, 구매, 병, 시음을 구분한다. 모든 화면에서 같은 판본·
  용량·구매 맥락으로 대상을 식별한다. 병 번호는 구매 건 내부 번호이며 UUID를 대체하지 않는다.
- **D232 — 집계 범위:** 제품 전체 평균과 SKU 평균을 명시한다. SKU 평균은 그 SKU의 모든
  유효 구매 수량으로 가중한다. 재고 원가는 **SKU 실평단가×그 SKU의 미개봉/개봉 병 수**의 합이다.
  병 단위 원가이며 잔량 ml에 비례한 평가액이 아니다. 누적 구매 용량과 현재 남은 양도 구분한다.
  개봉 잔량 미기록을 가득 찬 병 또는 0ml로 표시하지 않는다.
- **D233 — 반올림:** Decimal로 중간 평균을 반올림하지 않는다. SKU별 원가를 소수 2자리
  HALF_UP으로 확정하고 제품/전체 원가는 그 값의 합으로 한다. 표시용 평균 가격과 100ml당
  가격은 최종 출력에서 소수 2자리로 확정한다. UI 원 단위 표시는 계산 입력으로 재사용하지 않는다.
- **D234 — 가격·필터:** 기본 100ml당 가격은 정가, 실구매가 비교는 별도 필드다. 공란 구매가는
  0원이고 구매 없는 규격의 평균은 null이다. 구매 조건은 같은 구매 건에서 동시 충족한다.
  판본/SKU 미확인 비교는 확정 가격 비교로 표시하지 않는다. 과거 금액 원본은 변경하지 않는다.
- **D235 — 상태 보호:** 조건부 취소는 대상 동작 이후 같은 병의 후속 변경을 덮어쓰지 않는다.
  저장 완료는 제출한 초안 버전만 정리한다. 계정 전환·중복 요청·동시 수정에서도 같은 계약을 유지한다.
- **D236 — 정정·호환:** 정정은 기존 ID·시음·첨부·QR 연결과 감사 이력을 보존한다. 필요한
  API는 추가형으로 설계하고 기존 PWA 응답 형식을 유지한다. 파생 SKU 요약은 DB에 저장하지 않는다.
  기존 expected revision/receipt/event 구조를 먼저 재사용한다. 새 저장 필드가 필요하면 해당
  PR에서 schema·기존 데이터 보존·복구 검증을 명시하며 전역 재번호·자동 정리는 하지 않는다.

- **D237 — 사용 규격 보호:** 삭제된 구매·시음도 SKU 사용 이력으로 센다. 명시적 온라인
  규격 생성은 참조·바코드·포장 메모가 전혀 없는 삭제 SKU만 같은 ID로 재사용할 수 있다.
  그 외 원본은 보존하고 충돌을 알리며 sync의 새 entity ID를 다른 ID로 치환하지 않는다.
- **D238 — 조건 가격:** `filtered_prices`·`filtered_stock_count`로 조건 모집단을 전체 지표와
  구분한다. 가격 정렬·범위·커서는 반올림 전 같은 값, 표시 금액은 기존 소수 2자리다.
  비가격 병수 정렬은 제품 전체 지표를 유지한다. 구매 조건은 상세 URL·CSV에서도 드러낸다.

- **D239 — 명시적 정정:** 현재 잔량은 기본 유지하며 `set_final`에서만 양쪽 병의 최종값을 적용한다. 구매 정정은 삭제된 자식도 ID·버전 집합에 포함한다. 미사용 목표 SKU의 용량 변경도 검사하고, 날짜·대상 변경은 최종 병의 알려진 개봉/종료일 범위를 검증한다. 기존 날짜 미기록과 내용만 수정하는 legacy 불일치는 보존한다.
- **D240 — 정정 재시도·탐색:** 요청 ID와 원본 전제조건을 초안에 보존하고 네트워크·5xx 결과 불명은 같은 요청으로 확인한다. 409는 명시적 재확인을 요구한다. 과거 receipt를 로컬에 덮지 않고 최신 pull로 갱신하며, 제출 후 사용자가 이동한 맥락은 늦은 성공으로 바꾸지 않는다.

- **D241 — 최종 수용 보완:** 정정 폼의 원래 병·대상 병·SKU는 최초 최신 조회 후 승인 기준을 잡는다. 캐시가 fresh여도 재열기 조회를 생략하지 않으며 작성 중 기준은 자동 갱신하지 않는다. 홈 최근 시음은 전체 이력과 같은 날짜/ID 순서·유효 부모 검사를 쓴다.

- **D242 — 1.9.0 운영 수용:** usage/S01~S20과 필수 CI 후 태그 전/전환 직전 전체 백업을 각각 격리 복원했다. 운영 0019→0020에서 기존 행·ID·암호문·DB/uploads 볼륨 보존을 확인했다. 패키지·태그·이미지·실제 배포 SHA를 구분하며 구 스키마로 자동 되돌리지 않는다.

### 4.2 가격·검색의 모집단과 정답

검색 결과의 가격 필터·정렬값은 아래 모집단 M으로 계산한다. 제품을 먼저 임의의 첫 SKU로
대표시키지 않는다. 필터 적용 화면에는 "조건에 맞는 구매 평균"을 표시하고, 전체 이력 평균을
함께 보여줄 때는 별도 이름을 붙인다. SKU별 재고 원가(D232)는 항상 해당 SKU 전체 유효 구매의
평균을 사용하며 검색 가격 모집단으로 원가 정의를 바꾸지 않는다.

| 사용 맥락 | 계산할 구매 모집단 / 표시 기준 |
|---|---|
| 목록에 구매·용량·재고 조건 없음 | M=제품의 모든 유효 구매. 제품 가격 정렬은 전체 용량 구매 평균 |
| 용량 선택 | M=그 용량 SKU의 모든 유효 구매. 선택 SKU 평균으로 제품 가격 필터·정렬 |
| 구매처·구매일 조건 추가 | M=위 범위에서 같은 구매 건이 모든 구매 조건을 충족한 집합 |
| 재고 있음 조건 추가 | 위 조건에 맞는 구매에 미개봉/개봉 병이 남아 있는 SKU만 포함. M은 그 SKU에서 위 구매 조건을 만족하는 전체 구매이며, 같은 SKU의 과거 구매도 평균에 포함. "재고 있는 규격의 구매 평균"으로 표시 |
| 재고 없음 조건 추가 | 용량/구매 조건이 없으면 **제품 전체 재고 0**인 제품만 포함. 용량/구매 조건이 있으면 그 범위의 재고가 0인 결과만 포함하고 "조건 내 재고 0"과 제품 전체 재고를 구분. 구매 없는 제품은 가격 null |
| 목록 평균 실구매가/정가 정렬 | M의 수량 가중 평균. 0원도 포함, 구매 없는 null은 양 방향 모두 뒤. 동률은 제품 ID로 고정 |
| 100ml당 가격 범위·정렬 | M의 총 정가÷총 구매 용량×100. 기본 정가 기준 유지. 실구매 비교는 별도 값 |
| 상세·매장 규격별 최근/최저/평균 | 선택 SKU의 전체 유효 구매. 최근=구매일 내림차순(미기록 뒤)·created_at·ID, 최저=병당 실구매가, 평균=수량 가중 실구매가. 각 기준을 이름으로 표시 |
| 외부 제안의 내 가격 대비 | 식별·판매 조건이 확인된 선택 SKU의 전체 실구매 평균을 100ml로 환산한 값. 최신 구매가로 임의 대체하지 않음. 기준 null이면 구매 이력 없음, 0원이면 비율 비교 불가 |

구매처·구매일 조건이 있으면 이를 **같은 구매 건에서 충족하는 구매가 최소 하나** 있어야 한다.
빈 구매 집합을 "재고 없음"으로 간주해 검색에 다시 포함하지 않는다. 구매 조건 없이 조회하는
기존 미구매 제품/SKU만 가격 null·재고 0으로 포함한다. 용량 조건이 있으면 그 용량 SKU가
실제로 존재해야 한다. null 가격은 가격 범위 조건을 충족하지 않는다. G06의
A매장＋2026년＋재고 없음 역시 불일치다.

기존 가격 랭킹의 0원 제외(D215)는 유지한다. 검색의 0원과 랭킹의 제외를 섞지 않는다.
목록 조건을 상세로 넘겼을 때는 해당 구매들을 표시/강조하되 상세의 "전체 구매 이력"과
"선택 조건"을 전환할 수 있게 한다. 값의 모집단이 바뀌면 제목도 함께 바뀐다.
G07의 두 정렬 순서와 G08의 0%가 S13/S14의 독립 정답이다.

### 6.2 검증과 완료 조건

- 자동화는 표시 문자열뿐 아니라 영향을 받은 제품/SKU/구매/병/시음 ID와 실제 잔량을 확인한다.
  계산 기대값을 동일 구현에서 생성하거나 API·웹의 상호 일치만으로 정답을 판단하지 않는다.
- 각 기능 PR에서 해당 실브라우저 흐름을 직접 수행한다. 입력/선택/전환 과정의 우회 설정을
  명시하고, 해당 기능 자체를 API seed로 대체하지 않는다. 바코드 판독/외부 경계는 mock과
  실제 기기 검증을 구분한다. 기존 v1.8.2 PWA와 새 API의 호환·대기 명령도 검사한다.
- `development.md` §2의 Ruff·ty·웹 check·secret scan과 변경별 전체 테스트·CI를 수행한다.
  Python branch 85%, 웹 80%를 유지한다. schema 변경 시 별도 폐기 DB의 왕복·drift·기존
  ID/암호문 보존·격리 복원까지 추가한다. 무관한 동일 검증의 반복은 피한다.
- 최종 기록은 사용자 질문에 대한 답을 먼저 제시한다: 무엇이 남았나 / 얼마에 샀나 /
  어느 병을 기록했나 / 실수를 어떻게 고치나. 스크린샷·민감정보 없는 로그와 원본 ID 대조를
  근거로 연결한다. 가로 넘침 없음·HTTP 200·커버리지 충족만으로 사용성 수용을 선언하지 않는다.
