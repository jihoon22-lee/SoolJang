지난 릴리스·Task·결정 로그(D1~D211)는 [history.md](history.md), 동작 설계는
[architecture.md](architecture.md)·[external-data.md](external-data.md), 개발·검증 절차는
[development.md](development.md), 운영·배포는 [operations.md](operations.md)를 따른다.

> **갱신 규칙**: 모든 작업 PR은 §1(현재 위치), §2(진행 표), §4(결정), §5(열린 질문) 중 바뀐

## 3. 재개 절차

1. `git status -sb`, `git log --oneline -5`, 열린 PR과 원격 main을 대조한다. 미커밋 변경과
   진행 중 PR을 보존하고, 재개 작업은 기존 브랜치를 쓴다. 자동으로 main으로 바꾸지 않는다.
2. §1·§2 → 메인 이슈 → 관련 코드와 하위 `AGENTS.md` 순으로 읽는다.
3. 환경이 필요할 때만 [development.md](development.md) §1로 격리 DB·앱을 준비한다.
   이 기기의 Compose는 운영 스택이다.
4. [development.md](development.md) §2의 변경별 검증을 하고, 계획·구현·실검증·배포를 구분해
   `workthrough/`에 남긴다.

## 4. 결정(v1.8.0, D212~)

릴리스 후 [history.md](history.md) §6으로 옮긴다.

| 결정 | 내용 | 근거 |
|---|---|---|
| D212 | 사용자가 "오늘"로 기록하는 날짜는 기기·설정 시간대(`SOOLJANG_TIMEZONE`, 기본 Asia/Seoul) 기준이다 | 클라이언트 `toISOString()`·컨테이너 UTC 때문에 한국 00~09시 개봉·시음·구매가 전날로 저장됐다(리뷰 실측: 00:06 KST 테스트가 전날 날짜로 실패) |
| D213 | 다른 기기의 변경과 부딪힌 병 상태 전이는 실패가 아니라 `conflict`(서버 상태 유지·ConflictLog)로 돌려주고 배치를 계속한다. 오프라인 시음은 잔량이 부족해도 기록을 보존(잔량0·소진)한다. 실패 명령이 남아도 pull은 계속한다 | 정상적인 다기기 경합 하나가 대기열 전체와 받기를 멈추던 결함. 입력 자체의 검증 실패는 기존처럼 head-of-line으로 멈춘다 |
| D214 | 제품 삭제는 하위 규격·구매·병을 같은 시각으로 soft delete 한다(시음은 보존). 이전 버전에서 남은 하위 행은 조회 경계에서 부모 삭제를 함께 확인해 제외한다 | 구매 삭제와 같은 규칙. 운영 원본을 일괄 수정하는 migration 대신 조회를 바로잡는다 |
| D215 | 할인율은 정가가 기록된(0원 초과) 구매만으로 계산한다. 가격 순위(병당·총액·100ml당)에는 0원 제품을 넣지 않는다. 합계·평단가의 0원 포함(D211)은 유지한다 | 정가 공란+실구매가만 있는 구매가 할인율을 음수로 만들고, 선물 0원이 "가장 싼 술"처럼 순위를 채웠다. D211의 순위 포함 기대를 이 결정으로 대체한다 |
| D216 | 소진 되돌리기는 0이 된 잔량을 미기록으로 돌리고, 개봉 병 잔량을 직접 맞추는 `:remaining`/`set_remaining`을 둔다(0이면 소진). 개봉일보다 앞선 시음은 개봉일을 그날로 당긴다 | 되돌린 병에 시음하면 "잔량 부족"으로 막히고 고칠 UI가 없었다. 앞선 시음으로 소진되면 소진일<개봉일 제약에 걸려 저장이 거부됐다 |
| D217 | 여러 병 상태 전이는 병마다 outbox 명령 하나로 적재한다(별도 batch API 없음). 확인창 대신 즉시 반영 + 실행 취소(역방향 전이)를 쓰고, 증여·판매만 날짜·메모 시트로 한 번 더 받는다 | 오프라인 지원·충돌 처리(D213)를 그대로 재사용한다. 서버 batch API는 부분 실패·오프라인 정합성을 새로 설계해야 해 이득이 적다 |
| D218 | 보관 위치 일괄 이동(`PUT /collection/bottles:move`)은 전부 성공 또는 전부 취소, 실사 일괄 스캔(`scans:batch`)은 항목별 결과다. 실사 위치 반영(`:apply-locations`)은 사용자가 누를 때만 한다. 실사 관찰은 JSONB 저장을 유지한다 | 위치 이동은 중간 실패 시 일부만 옮겨지면 확인이 어렵다. 관찰 테이블 분리는 개인 규모(재고 수백 병)에서 행 재작성 비용이 작아 운영 데이터 migration 위험이 더 크다 |
| D219 | 구매 병수 변경은 온라인 PATCH로만 하며, 줄일 때는 번호가 큰 미개봉 병만 지운다(부족하면 409). 동기화 update의 `quantity`는 거부한다 | 이미 마시거나 내보낸 병의 시음·이력을 조용히 지우지 않는다. 병 추가·삭제·번호는 서버 기준이어야 한다 |
| D220 | 모바일(<600px)은 주 탭을 하단 탭바로, 통계는 탭으로 나누고, 화면마다 핵심 지표 3개만 크게 보인다. 본문 글꼴은 시스템 한글 글꼴(내려받지 않는 Pretendard 선언 제거), 숫자는 고정폭 숫자로 쓴다 | 모바일 헤더가 화면의 20%, 통계가 세로 4,600px이었다. 웹 글꼴 내려받기(약 2MB)를 오프라인 precache에 넣지 않는다 |
| D221 | "오늘 마셨어요"는 홈에서 병 고르기 → 별점·따른 양 → 저장 두 단계다. 시음 입력은 날짜·별점(0.5 단위)·양 프리셋을 먼저, 향·맛 등은 접어 두며 직전 장소·동석자를 기기에 기억한다 | 한 잔 기록에 제품→병→8칸 폼을 거치던 흐름을 줄인다. 저장 규칙은 기존 `record_tasting` 과 같다 |
| D222 | 병 상태 전이·잔량 조정·시음으로 인한 병 변화와 구매 수정을 `record_event`(0019, additive)에 바뀐 칸만 [이전, 이후]로 쌓는다. 온라인·동기화가 같은 서비스 함수를 거쳐 한 번만 남고, 과거 이력은 소급하지 않는다 | 실행 취소·실수 확인의 근거. 재계산할 수 없는 1차 사실이라 저장한다. 위치 이동은 기존 `bottle_movement` 와 합쳐 보인다 |
| D223 | 개봉 후 권장 기간 알림은 서버 푸시가 아니라 홈 위젯으로 하고, 주종 경로 이름(와인 7일·맥주/막걸리 3일·청주/사케 30일·주정강화/리큐르 90일, 증류주 없음)으로 고른다. 규격별 지표·CSV 내보내기는 오프라인 계산으로 한다 | 새 서버 작업·알림 동의 없이 바로 쓸 수 있다. 푸시 확장은 실제 사용 뒤 판단한다 |
