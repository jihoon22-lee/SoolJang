# 자체 통합 테스트·다각도 분석 결과 (Task 21, 2026-08-03)

Task 21의 산출물이다. 실데이터(제품 405~406종·병 1,078~1,079개·구매처 64곳)로 직접 써
보며 찾은 문제, 그 문제를 실행한 Task 22 개선(#26~#35, 10개 PR), 그리고 남은 항목을
정리한다. `docs/plan.md` §1의 "Task 22 실행 요약"이 PR별 상세·근거·결정 로그를 담고
있으므로, 이 문서는 **관점별로 재정리**하는 데 집중하고 세부 사항은 그쪽을 참조한다.

## 요약

Task 22 실행 전 감사에서 발견한 핵심 문제는 "백엔드 API·테스트는 있는데 UI 가 없어 쓸 수
없는 워크플로가 여러 개"였다 — 재구매, 구매 건 삭제·분할, 규격 추가, 제품 정보 수정,
시음 기록 삭제, 비밀번호 변경, 구매처 관리 화면, 6종의 미노출 필터. 이 갭 대부분을
PR3·PR6 에서 메웠다. 그 위에 사용자가 명시한 두 가지 요구(디자인 전면 개편, 이 앱의
본래 사용 시나리오인 "매장에서 즉석 조회")를 PR8·PR9·PR10 으로 실행했다.

## 관점별 분석

### 입력 효율

- **문제**: 재구매(같은 술을 다른 곳에서 또 사는 것)에 대응하는 UI 가 없었다 — 이 앱의
  가장 기본적인 워크플로 중 하나인데도 신규 등록 폼에서만 구매를 만들 수 있었다
- **개선(PR3)**: 제품 상세에 "구매 추가" 버튼 + 삭제·분할 추가
- **개선(PR7)**: 이름·구매처 자동완성(접두사 → 단어 시작 → 부분 일치 순위, 한글 초성
  검색 "ㄱㄹㄱㅇ" → "글렌고인"), 구매일 기본값=오늘, 구매처 기본값=직전 사용값
  (localStorage), 중복 등록 시 "구매 이력 추가하시겠어요?" 로 재구매 유도
- **개선(PR10)**: 매장 모드에서 바코드 스캔 또는 이름 검색 한 번으로 "이거 전에
  얼마에 샀지?"에 즉시 답한다 — 그 술을 찾기 위해 목록을 훑을 필요가 없다
- **남은 것**: 여러 제품을 한 번에 수정하는 대량 편집은 이연했다(백로그, `plan.md` §9)
  — 개별 수정이 먼저이고 실제로 불편한지 써 보고 판단하기로 함

### 정보 밀도

- **문제**: 이름 옆에 `(2018)` 처럼 빈티지가 붙어 있어 목록에서 구분하기 어려웠고,
  405행을 스크롤하면 헤더가 사라졌다. 405×64 규모의 목록에 스크롤이 과하게 길어지는
  문제도 있었다(사용자 보고)
- **개선(PR2)**: 빈티지 전용 열 분리, 헤더 클릭 정렬(`aria-sort` 포함), 스티키 헤더,
  세로 padding 축소
- **개선(사용자 요청 대응)**: 405행 제품 카드·64곳 구매처 목록 등에 `max-height` +
  `overflow-y: auto` 를 적용해 페이지 자체가 과도하게 길어지지 않게 했다(PR8 디자인
  개편과 함께 적용, `.product-cards`/`.vendor-list`/`.category-tree`/`.bottle-list` 등)
- **개선(PR8)**: `.app-main` 최대 폭 확대, 카드/표/버튼 컴포넌트 톤 통일("Cellar Dark"
  디자인 시스템 — 사용자가 4개 시안 중 직접 선택)

### 탐색

- **문제**: `useState` 만으로 화면을 전환해 URL 이 바뀌지 않았다 — 뒤로가기를 누르면
  앱을 완전히 벗어났다. 통계에서 특정 제품·주종을 봐도 그 제품 상세나 필터로 건너뛸
  방법이 없었다
- **개선(PR1)**: `history.pushState`/`popstate` 기반 해시 라우팅(`#products/<id>`,
  `#products?category=<id>` 등). 제품 상세 진입 전 스크롤 위치를 기억했다가 뒤로가기
  시 복원
- **개선(PR5)**: 통계 랭킹 항목 → 제품 상세, 주종별 집계 행 → 그 주종 필터가 걸린
  목록으로 크로스 링크
- **개선(PR10)**: `#scan` 을 1급 화면으로 승격 — "마트에서 앱을 켠다"는 시나리오가
  더 이상 "바코드 스캔 버튼을 목록 화면에서 찾아야" 하는 부수 기능이 아니다

### 통계 유용성

- Task 20(통계 v2)에서 이미 커스텀 피벗·시계열·저장뷰까지 구현했다 — 이번 배치는 그
  결과로 가는 경로(크로스 링크)만 개선했다(PR5). 새로운 지표 자체는 추가하지 않았다

### 접근성

- PR2 의 헤더 정렬에 `aria-sort`, PR7 의 자동완성에 ARIA combobox 패턴
  (`role="combobox"`/`aria-expanded`/`aria-activedescendant`)을 적용했다
- PR8(디자인 개편) 진행 시 기존에 확보된 것(명암비 4.5:1, 44px 터치 타깃,
  `:focus-visible` 아웃라인, skip-link)을 새 디자인에서도 유지하는 것을 명시적 제약으로
  뒀다 — 회귀 없음을 각 컴포넌트 재검토로 확인
- **남은 것**: 스크린리더 실사용 검증은 자동화 테스트(`getByRole`/`aria-*` 어서션)로
  간접 확인했을 뿐 실제 스크린리더로 훑어본 적은 없다 — 배포 후 확인 항목

### 성능

- **문제(사용자 보고)**: 병 "소진" 버튼 클릭 시 프레임 드랍 체감
- **원인**: `sync/queries.ts::assembleProducts()`가 매번 4개 테이블(product·sku·
  purchase·bottle) 전량을 로드해 405개 제품 지표를 재계산했다. 병 하나를 소진 처리하면
  ① outbox 낙관적 쓰기 ② 즉시 동기화 트리거(디바운스 없음) ③ 서버 응답 재적용
  ④ 델타 풀 결과를 트랜잭션 없이 행 단위로 `put()` — 이 네 단계 각각이 `useLiveQuery`
  재평가를 유발해 클릭 1회에 "전량 스캔 + 지표 재계산"이 수~수십 회 일어났다
- **개선(PR4)**: `pullDeltas`/`flushOutbox` 의 쓰기를 `db.transaction()` 으로 묶어 재평가
  1회로 합치고, `OUTBOX_CHANGED` → `triggerSync` 에 300ms 디바운스 추가
- **함께 발견·수정**: 병 개봉 → 미개봉 되돌리기 UI 가 없었던 것(사용자가 실수로 개봉을
  눌러도 되돌릴 수 없었다)도 같은 PR 에서 해결
- **서버 쪽에서 발견·수정한 별개 문제**: 레거시 CSV 대량 임포트(429행) 직후 곧바로
  목록·통계를 조회하면 정상 4~6ms 걸리던 쿼리가 **25~30초**로 느려지는 현상을 실측으로
  발견했다. `autovacuum` 의 `ANALYZE` 는 보통 수십 초~1분 뒤에나 돌기 때문에, 방금 넣은
  데이터를 곧바로 조회하면 플래너가 "빈 테이블" 기준 옛 통계로 `user_id` 선택도를
  오판해 해시 조인 대신 중첩 루프를 골랐다. `application/legacy_import.py::apply_plan`
  이 적재 직후 영향받은 8개 테이블에 `ANALYZE` 를 직접 돌리도록 수정했고,
  `pg_stat_user_tables.last_analyze` 로 회귀 테스트를 남겼다
- **실사용 규모·10배 규모 응답 시간 실측(2026-08-03, `tests/performance/
  test_scale_benchmarks.py`, opt-in)**:

  | 엔드포인트 | 실사용 규모(제품 429·병 1,078) | 10배 규모(제품 4,290·병 10,780) |
  |---|---|---|
  | `GET /products`(첫 페이지 50건) | 118.3ms | 104.6ms |
  | `GET /stats/summary` | 120.7ms | 183.5ms |
  | `GET /stats/by-category` | 22.7ms | 109.8ms |
  | `GET /stats/rankings` | 25.3ms | 134.8ms |
  | `POST /stats/pivot`(구매처×주종) | 25.6ms | 210.8ms |
  | `GET /stats/timeseries` | 16.5ms | 33.7ms |

  모두 여유 있게 빠르다 — 10배 규모에서도 체감 지연이 생길 요인이 없다(가장 느린
  `POST /stats/pivot` 도 211ms). 하드 기준으로 강제하지 않는 이유·재현 방법은 테스트
  파일 docstring 참조

### 오류 회복

- **문제**: 개봉을 실수로 눌러도 되돌릴 방법이 없었다(위 성능 항목과 같은 PR4)
- **문제**: 처리되지 않은 예외(DB 연결 실패로 재현·발견)가 이 API 의 문서화된 계약
  ("에러는 RFC 9457 Problem Details 형식이다")을 어기고 순수 텍스트 500 응답을 그대로
  노출했다
- **개선**: `api/errors.py` 에 `Exception` 캐치올 핸들러를 추가해 어떤 처리되지 않은
  예외도 Problem Details 형식으로 감싸고, 원인(스택 트레이스)은 서버 로그에만 남기게
  했다(`logger.exception`). `tests/api/test_error_handling.py` 로 검증 —
  `get_session_factory` 를 깨진 것으로 바꿔치기해(`monkeypatch`) 실제 DB 를 내리지
  않고도 접속 실패와 같은 예외 경로를 재현하고, 그 요청이 500 이어도 다음 요청은
  정상 처리됨(커넥션 풀·세션 상태가 오염되지 않음)까지 함께 확인한다
- **개선**: 라벨 인식(`infrastructure/external/llm.py::extract_label`)의
  `except Exception` 이 인증·형식 오류뿐 아니라 네트워크 타임아웃(`httpx.ConnectTimeout`)
  도 같은 `LabelExtractionFailedError` 로 통일해서 던지는지 장애 주입 테스트로 확인 —
  `httpx` 예외가 그대로 새어 나가 500 으로 보이는 걸 막는다
- **회귀 방지**: 위 두 항목을 포함해 등록→검색→구매 분할→개봉→시음→통계→바코드→피벗→
  저장뷰→오프라인 동기화까지 한 번에 잇는 E2E 시나리오 테스트
  (`tests/api/test_e2e_scenario.py`)를 영구 회귀 테스트로 추가했다 — 이번 검증에서
  일회성으로 확인하고 끝내지 않고, 앞으로도 계속 도는 테스트로 남겼다

### 데이터 안전

- **백업 → 복원 → 통계 재계산 무결성 검증(2026-08-03 수행)**: 실데이터
  DB(`sooljang`, 제품 406종·병 1,079개·구매처 64곳·구매 435건)를 대상으로
  1. 재계산 전 스냅샷: `/stats/summary`·`/stats/rankings`(상위 10)·
     `/stats/by-category` 를 애플리케이션 코드(`application/stats.py`)로 직접 실행해
     JSON 으로 저장
  2. `pg_dump -Fc` 로 백업
  3. 새 빈 데이터베이스에 `pg_restore`(오류 0건)
  4. 복원본에 대해 같은 계산을 재실행
  5. 두 결과를 비교 — **완전히 동일**(테이블별 행 수 9종 포함)

  결론: 백업이 실제로 복원 가능하고, 복원된 데이터에서 파생 지표가 원본과 정확히
  같은 값으로 재계산된다. 임시로 만든 DB 는 검증 직후 삭제했다
- **동기화 충돌**: `test_sync.py` 가 이미 LWW(늦은 로컬 변경 폐기 후 `conflict_log`
  기록), idempotent resend(같은 idempotency_key 재전송 시 중복 처리 안 함),
  head-of-line blocking(배치 중 하나 실패 시 그 이후를 멈춤)을 검증하고 있었다 — 이번에
  새로 발견한 문제는 없었다
- **외부 소스 장애**: PR9 의 `test_adapter.py` 가 검색/상세 페이지 HTTP 오류, robots.txt
  차단(검색·상세 각각), 셀렉터 파손(부분 결과), 후보 없음/유사도 부족을 전부
  `degraded=True` + 경고 메시지로 처리함을 확인(예외로 전체 조회를 막지 않음)
